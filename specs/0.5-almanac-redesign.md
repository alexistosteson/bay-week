# Spec 0.5 — Almanac visual redesign

**Tier: probe.** The deliverable of *this* branch is a look at the mockups, not a
merge. Nothing here goes to `main` on the strength of this spec: promoting the
Almanac to the published site is a separate, **build**-tier spec, which will owe
a plan, a NASA audit and the merge ritual. Declaring probe here is a statement
about what this branch is for, not a route around that.

## What

Recreate the **Almanac** direction from `Website design exploration.zip`
(`design_handoff_bay_week_almanac`) in this codebase's shape — one HTML file,
one JSON file, no framework, no build step beyond `build.py`, no runtime request
except Google Fonts.

Three things the current site does not have:

1. Filters behind a `¶` overlay (full-screen takeover on phone).
2. A **How to get there** panel per event — Maps route, derived drive time and
   corridor, time-of-day warning, parking, transit.
3. A **Plan** shortlist with hash-shareable state and a won't-make-it check.

## Non-negotiables carried from the brief

Light only, no `prefers-color-scheme`. Region encoded by a monotonic lightness
ramp, never hue alone. Region readable as text at all times. 4.5:1 minimum.
State in the URL hash. **No Bay Area geography in `index.html`** — origin,
region names/order/colours and the travel tables all arrive via `events.json`.

## Data the design needs that the pipeline does not produce

`travel:` block in `config/brief.yml` — a venue table (lat/lng, parking,
transit) and a corridor table (label, mph, toll, geometric test, peak windows).
`build.py` projects it onto `meta.travel` exactly as it already projects
`regions`. Derivation (haversine, drive time, corridor, departure, conflicts)
lives in the page; there is no traffic API and there must not be one.

## Behavioural check (owner)

Open the page. Scan the week; open the `¶` overlay and narrow it; open a
`… drive →` on a row; save two events on the same day and open Plan. Then the
same on a 390px viewport. Mockups stand in for the first pass.
